## Part 2 - Lecture Questions

### 1. What is BOLA, and why cannot a WAF reliably stop it?

BOLA means Broken Object Level Authorization. It happens when the API accepts an object ID but does not check whether the current user can access that object. It is ranked API1 because object IDs appear in many endpoints and a simple ID change can expose other users' data. A WAF usually sees a normal request such as `/api/users/3/orders`; it does not know the application's ownership rules.

### 2. What is mass assignment? Blocklist versus allow-list?

Mass assignment happens when the server copies client input directly into a user or another data object. An attacker can include fields such as `is_admin` that a normal user should not control. A blocklist rejects known dangerous fields, so a new sensitive field might be missed. An allow-list accepts only approved fields, such as `username` and `password`, and ignores everything else.

### 3. Two impacts of an unthrottled login endpoint

The security impact is password guessing: an attacker can try many passwords until one works and take over an account. The availability impact is resource exhaustion: many requests use CPU, connections, and database work, especially when password hashing is expensive. Real users may then face slow responses or a service outage.

### 4. Why is X-User-Id not authentication?

The client can change this header to any user ID, including Carol's admin ID. The server has no proof that the request comes from that user. Replace it with a verified session or token created after a successful login, and get the user ID from that trusted session. Even the course reference still trusts this header, so its ownership check is only a demonstration until authentication is fixed.

### 5. Why check authorization per request and per object?

Logging in only proves identity; it does not give permission to read every object. A user can request a different ID after login, and roles or ownership may change over time. Each request must check the current identity against the specific object and the current access rules on the server.

## Part 4 - Reflection

### 1. Finding mapping

| Finding | Endpoint | OWASP API ID | Fix |
| --- | --- | --- | --- |
| Other users' orders can be read | GET /api/users/<id>/orders | API1:2023 | Verified identity plus ownership/admin check |
| User can set admin and balance | POST /api/users | API3:2023 | Allow-list and server-controlled sensitive fields |
| Unlimited password guesses | POST /api/login | API4:2023 | Five attempts per IP per 60 seconds |
| Forged identity header in reference | GET /api/users/<id>/orders | API2:2023 | Verified expiring session instead of X-User-Id |

### 2. Real breach - Optus

The Optus breach became public in September 2022. In its 8 August 2025 statement, Australia's OAIC described unauthorized access to millions of customers' personal data and recommended checking that requests for customer information are authorized [1].

For this lab, I map unauthorized access to other customers' objects to API1:2023. This is an analysis of the authorization failure pattern, not a claim that the source establishes a specific sequential-ID exploit. A correctly applied ownership check backed by verified authentication would stop a user reading another user's record through a protected endpoint. The reference check alone would not be enough because `X-User-Id` can be forged; all exposed routes also need protection.

### 3. Best mitigation

I would prioritize object-level authorization with verified authentication because it directly protects private user data across the API. Without it, an attacker can read sensitive records using normal-looking requests, even at a low rate. Allow-list binding and rate limiting still matter, since ownership checks do not stop unwanted field updates or login abuse.
